# PING · 퓨넥스울산장례 연동 구상 요약

본 문서는 **PING(이 프로젝트, Firebase 연동)** 과 **퓨넥스울산장례(Supabase)** 를 **데이터 공유 없이 링크 중심**으로 두는 전제에서, 스택 분리·리스크·양방향 링크 시 유의사항을 정리한 메모입니다.

---

## 1. Firebase vs Supabase, 스택을 나눌 때

| 구분 | 장점 | 단점 |
|------|------|------|
| **따로 유지** (PING=Firebase, 퓨넥스=Supabase) | 제품·계약·장애·비용 범위 분리, 배포·보안 규칙 독립, 서비스 성격에 맞는 기술 선택 | 운영·모니터링·인증 패턴 이중 학습, 공통 사용자/주문 연동 시 동기화·SSO를 직접 설계, 과금 비교가 어려움 |
| **한쪽으로 통합** | 인프라·인증·DB 패턴 단일화, 통계·리포팅 단순 | 기존 Firebase/Supabase 이행 비용, 데이터 모델 재설계, 마이그레이션 리스크 |

**정리:** 서비스·유저 풀이 분리되고 당분간 데이터를 섞지 않을 계획이면 **스택 분리도 타당**하다. 반대로 **동일 사용자·동일 주문을 양쪽에서 다뤄야** 하면 BaaS 통합보다 **인증/사용자 마스터만 통합**하는 방식을 먼저 검토하는 편이 안전하다.

---

## 2. 공유 데이터를 아직 구상하지 않고 “링크 연결”만 할 때

링크만 두는 것은 흔한 출발점이며, 아래는 **나중에 터지기 쉬운 지점**이다.

1. **로그인·세션 분리** — 한쪽 로그인이 다른 쪽에 자동 반영되지 않는다. URL에 민감정보를 실어 넘기면 보안·개인정보 이슈가 된다.
2. **딥링크·도메인·환경** — 스테이징/운영 혼동, 인앱 브라우저, 리다이렉트 실패. 베이스 URL을 한곳에서 관리할 것.
3. **UTM·전환·책임** — 유입 측정을 위해 UTM 또는 내부 ref 규칙을 최소한 합의할 가치가 있다.
4. **개인정보·약관** — 링크만 있어도 “어느 주체가 무엇을 처리하는지”가 모호해질 수 있다. 중복 수집·위탁 문구 점검.
5. **장애(SPOF)** — 링크 대상이 다운되면 진입 화면만 남는다. 안내 문구·임시 숨김 등 운영 플레이북.
6. **향후 “조금만 공유”** — 사용자 ID·주문 ID만 맞추고 싶을 때 **source of truth** 가 없으면 데이터가 갈라진다. 지금은 공유가 없어도 “이 ID는 어느 시스템 소유인지”만 약속해 두면 이후 혼선이 줄어든다.
7. **브랜드·신뢰** — 외부 도메인으로 넘어가 사기 링크처럼 느껴질 수 있으므로 짧은 설명·공식 도메인 안내가 도움이 된다.

---

## 3. 양방향 링크가 될 때 (A↔B)

공유 DB 없이도 **대칭 품질**을 맞추는 것이 부담이 된다.

| 영역 | 권장 인식 |
|------|-----------|
| **UX** | A→B와 B→A 모두 뒤로 가기, 현재 서비스 안내(도메인·한 줄 설명) 수준을 맞출 것. |
| **계정** | 링크만으로 SSO/Cross-login은 되지 않는다. 필요 시 OAuth·공통 IdP 등 **별도 설계**. |
| **링크 계약** | 운영/스테이징 URL, 깨지면 안 되는 경로, 모바일·인앱 호환. 쿼리에 비밀번호·개인정보 금지; 필요 시 **짧은 만료·일회용 토큰**은 양측 합의 하에. |
| **분석** | 양방향이면 유입 방향 구분이 중요하다. UTM 또는 `ref=` 규칙을 짧게라도 통일. |
| **법무** | 서비스 전환이 두 번 일어나므로 개인정보·제3자 안내 문구가 시나리오와 맞는지 점검. |
| **장애** | 한쪽 다운 시 반대편에서 들어온 사용자도 막힌다. 링크 임시 비활성·안내 문구 등. |

**한 줄 요약:** 양방향은 **URL·UX·분석·토큰/보안**을 대칭으로 맞추는 일이 중심이고, **계정 통합은 링크와 별개**라는 전제를 팀과 공유하면 설계 공백에서 오는 착오를 줄일 수 있다.

---

## 4. 문서 목적

- 기술 결정서가 아니라 **구상 단계 메모**이다.
- 실제 URL·토큰 설계·SSO 도입 시에는 별도 보안 검토와 약관 반영이 필요하다.
